# Problem Statement and Threat Model

What may be hostile, what it wants, and which product answers which vector. Its companion, [the security model](security-model.md), says what is enforced against all of it — the mechanisms, and how strongly each one holds.

## The problem

Modern development environments collapse four very different trust domains into one session: editing and planning; dependency resolution and download; build and test execution; and credentialed operations such as push, signing, and publishing. In a typical local setup all four share the same filesystem view, network access, user identity, long-lived caches, and SSH, GPG, GitHub, and cloud credentials.

That is convenient and badly mismatched to the supply-chain threat landscape. Ordinary Rust and full-stack workflows routinely execute untrusted code before a human reviews it.

The core concern is not host isolation from a developer shell. It is isolation from **the software being developed** — its build tools, its dependency graph, and any agent-directed commands that execute it.

## Why Rust is a special case

Rust has a strong memory-safety story and a weak build-security model. Arbitrary code execution during development is a built-in feature of the ecosystem: `build.rs`, procedural macros, custom test binaries, doctests, linker wrappers, `cargo xtask`, and code generators invoked from cargo workflows.

So commands widely perceived as low risk are not: `cargo check`, `cargo build`, `cargo test`, `cargo metadata` in some workflows, and IDE or language-server background analysis. A crate update can run attacker-controlled code during compilation without the developer running anything that looks suspicious.

Full-stack development adds more of the same. `npm`/`pnpm`/`yarn` install, `postinstall` and lifecycle scripts, bundler plugins, test-runner plugins, ORM and codegen tools, and browser automation hooks all execute dependency or project-configuration code. Full-stack repos also pressure teams toward broad network access and real mounted credentials for local databases, service-to-service calls, third-party API tokens, and staging deployments — which directly undermines least privilege.

## What may be compromised

Clyde assumes any of these may be hostile: a source repository, a transitive dependency, a package registry account, a crate or npm or git dependency, a build script or proc macro, a test harness or browser hook, a command generated by an AI coding agent, or a long-lived cache or shared tool state.

## Attacker goals

An attacker with code execution in the development workflow may attempt to:

- exfiltrate SSH, GPG, GitHub, cloud, or package-publishing credentials
- tamper with the source tree or generated artifacts, or modify release outputs before signing
- move laterally into the host or other projects
- persist in caches, build directories, or long-lived containers
- reach external command-and-control infrastructure
- abuse an AI agent's execution privileges to expand access

## Attack vectors, and which product answers them

The two products do not cover these equally, and stating that here is the honest summary of what a given deployment defends against ([D23](builder/decisions.md#d23-the-mvp-splits-into-the-builder-and-the-warden)).

| Vector | Builder | Warden |
|---|---|---|
| **1. Malicious Rust dependency** — a transitive crate whose `build.rs` or proc macro reads secrets, hunts the workspace for credentials, or writes modified source | **addressed**: microVM, read-only snapshot, no egress, pre-execution inventory diff | — |
| **2. Malicious JavaScript package** — a lifecycle script exfiltrating environment variables, cookies, or tokens during install or build | post-MVP for `node.*`, same mechanism | — |
| **3. Compromised repository** — hostile build tooling, test hooks, or git hooks and configuration the developer or agent is likely to execute | **addressed**: sanitised git invocations, `.git` excluded from builds, hostile-hook hardening | adds a read-only `.git` mount |
| **4. Agent-assisted escalation** — an agent with broad shell access induced into exposing secrets, expanding mounts, or pushing tampered code | **partly**: typed tasks, leases, approvals, and audit constrain what Clyde will do — but nothing stops an uncontained agent acting outside Clyde | **addressed**: no toolchain, no credentials, no host home in the agent's environment |
| **5. Cache poisoning and persistence** — a compromised build step writing malicious state into shared caches or persistent volumes | **addressed**: per-mission caches destroyed at closeout, read-only dependency bundles, no VM reuse across runs | — |
| **6. Credential pivot during publish** — a build step that can also reach signing or push credentials replacing artifacts just before publication | **addressed** for the build sandbox; the broker's third function depends on the driver ([D8 amendment](builder/decisions.md#amendment-the-brokers-value-is-posture-dependent)) | makes it unconditional |

Vector 4 is the one that splits, and it is why posture is reported on every task run ([D26](builder/decisions.md#d26-enforcement-posture-is-explicit-reported-and-recorded)). The others are properties of what happens when a task runs, and a hostile dependency has no say in who requested the build.

## Assets to protect

SSH authentication capability; GPG or other signing keys; git hosting tokens and session state; cloud provider credentials; package registry credentials; browser cookies and authenticated sessions; the host machine and user account; the integrity of source, build outputs, and release artifacts; and the provenance records showing how an artifact was produced.

## Trust boundaries

A secure design separates at least these parts:

1. **Control plane** — trusted local supervisor enforcing policy
2. **Workspace environment** — reading, planning, editing, low-authority code manipulation
3. **Build environment** — build, test, codegen, package installation
4. **Broker environment** — push, signing, publishing, token issuance
5. **Artifact layer** — immutable inputs, caches, outputs, provenance

Boundaries 1, 3, 4, and 5 are the builder. Boundary 2 is the warden — and where it is absent, the editing environment is simply the developer's own machine, unconstrained by Clyde.

The two are different in kind, which is why they separate cleanly. The build environment is an **execution** boundary around code assumed hostile. The workspace environment is an **authority** boundary around a driver assumed careless rather than hostile. Confusing them produces designs that either over-constrain the human's editor or under-constrain the compiler.

These parts communicate through explicit, typed, auditable interfaces — never shared shells, mounted home directories, or forwarded credential sockets.

## Security objectives

- **Prevent credential exposure.** Untrusted build and test steps receive no raw SSH keys, GPG key material, cloud credentials, browser sessions, or general-purpose agent sockets.
- **Minimize filesystem visibility.** A task receives only the inputs that step requires, via immutable snapshots plus isolated scratch.
- **Deny network by default.** Compilation, testing, and code generation run without network unless a narrow task profile explicitly allows it.
- **Separate build from publish.** No environment executing untrusted project code may also sign, push, or publish.
- **Preserve agentic usefulness.** Iterative editing, build/test feedback, and automated assistance continue — through policy-controlled task execution rather than unrestricted shell access.
- **Support audit and provenance.** Each task produces enough metadata to understand what inputs, capabilities, and outputs were involved.

## The centralization/autonomy tension

Clyde should be the developer's single point of contact: one place where policy is enforced, credentials are brokered, approvals are requested, and audit is recorded. But effective agentic development depends on autonomous inner loops — repeated edit/compile/test iteration, specialized sub-agents, parallel work, retries and exploration without constant interruption.

These conflict only if "single point of contact" means the human must initiate every action. That reading would make the system too slow and push users back toward broad shell access. The resolution:

> Clyde is the sole **policy and authority** interface, but not the sole **actor**. Agents and sub-agents operate through Clyde under constrained, time-bounded, auditable capability grants.

Approval is required for boundary crossings, not for every safe inner-loop action.

## Non-goals

This design does not guarantee perfect defense against every kernel or hypervisor escape, fully reproducible builds for every ecosystem on day one, seamless compatibility with every local-dev habit, or zero-friction use of arbitrary external services from untrusted tasks. A compromised host resolver is out of scope.

The goal is meaningful least-privilege isolation with a practical developer experience, not total elimination of risk. [The security model](security-model.md) states what is enforced toward it, and grades each control by what an attacker would have to defeat.

## Desirable shape of a solution

Task-based isolation instead of one long-lived all-powerful dev container; separate environments for editing, execution, and privileged external actions; ephemeral sandboxes for untrusted steps; immutable snapshots for inputs and controlled artifact outputs; network denied by default with destination-scoped exceptions; brokered credentials rather than mounted secrets; typed operations each with a fixed policy; auditability and provenance; and a policy-aware execution API for agents.
